# Conversational application refinement: implementation and verification

Date: 2026-10-07. Host instruction version: `formative-conversation-host-v7.14`.
Release SHA and verified Render evidence are recorded in the appended release ledger
and its fixed Word report, separately from this pre-deployment evaluation.

## Implemented procedure

After the initial package, the existing tutor considers the complete responses,
current profile and visible conversation. It can connect related difficulties when
the student's reasoning supports that connection, distinguish separate difficulties,
respond directly to questions, or review a missing prerequisite. These are teaching
choices, not a compulsory sequence or a requirement to resolve every difficulty.

A brief application MCQ can be initiated by the tutor without a student request.
Question, options and an invitation for an option plus brief reason share one ordinary
chat message. There is no new response form, confidence check, activity record,
completion gate, assessment bank or research variable. Help, direct answers, flexible
replies, objections, topic changes and the existing pause/finish controls remain available.

The instructions distinguish accurate recognition from application after help. When
the tutor has supplied the answer and its explanation, restating that solution alone
does not authorize a new profile transition or claim resolution. This is a semantic
judgment about the information supplied, not a word-overlap test. A substantive short
explanation can still support a claim-specific change. Stronger independent-transfer
claims retain the existing separate evidence requirements.

The application still owns validation, persistence, lifecycle and profile transitions.
No context-builder, schema, validator, initial-assessment collection or student UI
was changed. The sole provenance adjustment recognizes v7.14 as carrying forward
initial confidence, not reassessing it. Existing historical records are not rewritten.

## Verification method

The added `conversational-application` suite uses three synthetic measurement items
and seven scenario families. Initial selections and explanations deliberately establish
the edge case; subsequent student messages are generated by an AI learner that sees
only the student-visible exchange and the instruction for its current turn. The tutor
uses the actual service, persistence, background preparation and approved model roles.
Each complete case has four learner replies after the opening.

All sessions use disposable local databases, not classroom accounts. Full provider
records, transcripts, source-file hashes, usage and research archives are retained in
ignored local evaluation folders. Mechanical outcomes are explicitly labelled as
requiring manual pedagogical review. The actual exchanges and structured evidence
were reviewed; a successful HTTP response alone was not counted as teaching quality.

| Scenario | Observed behavior and scope |
| --- | --- |
| Shared reliability/validity difficulty | Connected hiring and wellbeing through the student's stated assumption; responded to a school-placement question without forcing an MCQ; accepted finishing. |
| One correction, separate SEM difficulty | Final rerun recorded a claim-specific reliability/validity correction and explicitly retained the SEM claim, then respected declining SEM and finishing. No global understanding or compulsory completion was recorded. |
| Help before answering | Supplied the requested answer first. In the final rerun, the subsequent restatement produced recognition-with-scaffolding evidence and a null profile transition, then accepted pause. |
| Missing prerequisite and overview | Explained consistency, changed the level of explanation, answered an overview request and paused without a duplicate profile update. Recognition after explanation did not erase the SEM uncertainty in the final rerun. |
| Sound but low confidence | Acknowledged the correct reasons, distinguished confidence from correctness, accepted an explanation-only reply and respected declining further practice. Initial confidence was not remeasured. |
| Conflicting option and reason | Asked for clarification, preserved the original selection, responded to uncertainty and a direct explanation request, then allowed finishing with the remaining concern. |
| Objection, direct answer and decline | Discussed assumptions for SEM intervals, provided a worked answer on request and accepted finishing. The simulated learner answered rather than strongly objecting in the second run; this is not evidence that every flawed-example objection was exercised. |

The tutor initiated open application questions in reviewed openings. MCQs occurred
in the student-requested scenarios. Tutor-initiated MCQs are enabled by the instructions
and contract tests, but were not consistently elicited in this small sample.

## Defects found during evaluation

1. An early learner-generator prompt exposed the entire scenario script at once.
   The learner sometimes ended early, then returned an empty reply. The harness now
   supplies only the current turn instruction and requires a nonempty message.
2. A closing turn could duplicate an already validated profile update with no eligible
   new evidence. The validator rejected it. The instructions now distinguish a
   closing or overview request from a new learning judgment; the affected shared and
   prerequisite scenarios passed subsequent full reruns.
3. Two development runs overcredited a restatement immediately after the supplied
   answer and explanation. Overlapping instruction clauses were consolidated into
   the explicit recognition-only rule. The final help-first rerun preserved the
   profile and recorded the preceding scaffolding.
4. The build security gate identified newly vulnerable dependencies. Compatible
   patched versions of sharp, postcss-selector-parser and source-map-js were installed;
   argparse 2.0.1 removed the vulnerable sprintf-js dependency. Word-import CLI,
   image, stylesheet and document-import smoke tests passed. No new waiver was added.

The earlier failures remain in the evaluation artifacts; they are not counted as
passing sessions. This release does not weaken profile validators to accept them.

## Representative actual synthetic exchanges

These are excerpts, not human-student observations. Ellipses indicate omitted text.

**Partial improvement and student choice**

Student: "Consistent scores might reflect the wrong attribute in the hiring test too,
so reliability alone is not enough to establish validity. However, I still believe
subtracting the SEM from an observed score removes measurement error and gives the
exact true score."

Later student: "I don't want to work on SEM today. For the hiring test, what kind of
validity evidence would support using the scores to make hiring decisions?"

The tutor answered the hiring question. At the end, it retained the SEM distinction
under "Still worth working on" rather than forcing another exercise.

**Help before answering, final recognition-only rerun**

Student: "Could you help me determine the correct answer before I choose? I'm unsure
why C is better than A or B."

Tutor: "C is the best answer. ... It does not mean the student's particular error is
exactly 4 points or tell us its direction."

Student: "C is correct because the SEM describes typical measurement uncertainty,
not the exact size or direction of this student's error. Therefore, neither 64 nor
72 can be identified as the exact true score."

Tutor: "That distinction is correct: SEM describes typical measurement uncertainty;
it is not the student's known error."

The stored output was `continue_conversation`, null profile transition and an
observation recognizing immediate scaffolding. On "Could we pause here for now?",
the tutor acknowledged the pause; no further answer was required.

## Limits and educational interpretation

These tests support the specified service, logging and observed conversational
behaviors, not learning effectiveness, transfer, retention or diagnostic validity
across students. Classroom evidence and reviewed coding of explanations remain needed.

Generated practice examples can still be too similar to the preceding explanation,
and correct options can be more detailed than distractors. Instructions discourage
this, but the live sample did not establish consistent compliance. Such examples
are teaching opportunities, not validated outcome measures. Some replies remain
repetitive; numerical explanations can use broad assumption language that warrants
teacher review. Initial claim catalogs also vary across model runs: the complete
transcript and evidence observations must accompany any interpretation of profiles.

The final recognition-only and stop-request repairs were tested with targeted reruns,
not a claim that every stochastic output or every future 30-turn conversation is safe.
No full-capacity concurrent load test, browser UX study or human learning-outcome
experiment was conducted in this release. The unchanged validators provide structural
and provenance checks, not a complete semantic proof of pedagogical correctness.

Live configuration inspection found a 1,000,000-token session allowance and a
7,000-token per-conversation-call output allowance. The reviewed four-reply sessions
stayed below those limits, with no token-budget failure. No limit or model change was
needed. Total session tokens include input and output across all application calls;
they are not the length of a student-facing reply. Longer histories and retries can
increase consumption, so this is not a guarantee that any 30-turn history fits.
